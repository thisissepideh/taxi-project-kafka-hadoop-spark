## ۱. معماری

```
 داده خام TLC (Parquet)
        │
        ▼
 پاک‌سازی با pandas ──► yellow_clean.csv / .parquet
        │
        ▼
      HDFS  (Docker: NameNode, DataNode, ResourceManager, NodeManager)
        │
        ├──► MapReduce (Python Streaming و Java) ──► تعداد و میانگین مسافت روزانه
        ├──► Hadoop Streaming + Combiner ─────────► هیستوگرام مدت سفر
        │
        ▼
   Spark (batch, local) ──► فیلتر، میانگین مدت بر حسب منطقه، سرعت ساعتی

 Producer (Python) ──► Kafka (topic: taxi-trips) ──► Spark Structured Streaming
                                                        │
                                                        ▼
                                          جدول‌های Memory Sink ──► داشبورد زنده
```

## ۸. بخش ۴: MapReduce

**مسئله:** تعداد سفرها در هر روز و میانگین مسافت.

- **Mapper:** هر خط CSV را می‌خواند (هدر را رد می‌کند) و `تاریخ ↦ "مسافت,1"` تولید می‌کند.
- **Shuffle و Sort:** هدوپ مقدارهای یک تاریخ را کنار هم می‌آورد.
- **Reducer:** تعداد و جمع مسافت را جمع می‌زند و `تاریخ، تعداد، میانگین` را چاپ می‌کند.

کد با Python نوشته و با Hadoop Streaming اجرا شد. قبل از اجرا روی کلاستر با `cat | mapper | sort | reducer` روی ۵۰۰۰ خط اول تست شد.

### شمارنده‌های job (Python Streaming)

| شمارنده | مقدار |
|---|---|
| `Launched map tasks` | ۲ |
| `Launched reduce tasks` | ۱ |
| `Map input records` | ۲٬۷۱۱٬۷۹۵ (ردیف‌ها به‌اضافه هدر) |
| `Map output records` | ۲٬۷۱۱٬۷۹۴ |
| `Combine input / output records` | ۰ / ۰ |
| `Reduce input records` | ۲٬۷۱۱٬۷۹۴ |
| `Reduce output records` | ۳۱ (یک خط برای هر روز) |
| زمان | ۷۴٫۸ ثانیه |

## ۹. بخش ۵: Hadoop Streaming و Combiner

**مسئله:** توزیع مدت سفرها در بازه‌های ۵ دقیقه‌ای. چون Reducer فقط جمع می‌زند، همان کد به‌عنوان **Combiner** هم روی خروجی هر Mapper اجرا شد.

| شمارنده | بخش ۴ (بدون Combiner) | بخش ۵ (با Combiner) |
|---|---|---|
| `Map output records` | ۲٬۷۱۱٬۷۹۴ | ۲٬۷۱۱٬۷۹۴ |
| `Combine input records` | ۰ | ۲٬۷۱۱٬۷۹۴ |
| `Combine output records` | ۰ | **۷۲** |
| `Reduce input records` | ۲٬۷۱۱٬۷۹۴ | **۷۲** |
| `Reduce output records` | ۳۱ | ۳۶ |
| زمان | ۷۴٫۸ ثانیه | ۳۸٫۵ ثانیه |

عدد ۷۲ از ۲ Mapper ضرب‌در ۳۶ بازه (۰ تا ۱۸۰ دقیقه) به‌دست می‌آید. حجم داده Shuffle از ۲٫۷ میلیون رکورد به ۷۲ رکورد رسید.

> **هشدار مقایسه:** دو job این جدول کار متفاوتی می‌کنند (جمع مسافت و میانگین در برابر شمارش بازه‌ها)، پس اختلاف زمان آن‌ها را نباید به Combiner نسبت داد. کاهش رکوردهای Shuffle اثر قطعی Combiner است.

## ۱۱. بخش ۷: Kafka و Spark Streaming

### اجزا

- **Kafka** (KRaft، تک‌گره) با topic به نام `taxi-trips` و ۳ پارتیشن.
- **Producer** (`producer.py`): سفرهای تصادفی از داده پاک‌شده را به‌صورت JSON می‌فرستد (۹۰۰۰ پیام در هر اجرا).
- **Spark Structured Streaming:** سه کوئری همزمان با خروجی Memory Sink:
  1. `window_stats`: تعداد سفر، میانگین مسافت و میانگین مدت در پنجره‌های ۱۰ ثانیه‌ای (بر پایه timestamp پیام Kafka)
  2. `dist_hist`: توزیع مسافت در دسته‌های ۱ مایلی
  3. `zone_stats`: تعداد سفر و میانگین مدت به تفکیک منطقه

### نتایج

| مورد | مقدار |
|---|---|
| پیام ارسال‌شده | ۹۰۰۰ |
| پیام دریافت‌شده (`SUM(trips)`) | **۹۰۰۰** |
| تعداد سفر در پنجره ۱۰ ثانیه‌ای (پنجره کامل) | حدود ۸۷۰ (نرخ مؤثر حدود ۸۸ پیام در ثانیه) |
| میانگین مسافت پنجره‌ها | بین ۳٫۵ و ۴٫۰ مایل |
| میانگین مدت پنجره‌ها | بین ۱۴٫۸ و ۱۶٫۲ دقیقه |

نرخ مؤثر کمتر از ۱۰۰ پیام در ثانیه است، چون هر ارسال خودش زمان می‌برد و به `sleep` اضافه می‌شود. آخرین و اولین پنجره هر اجرا ناقص‌اند.

## ۱۵. محدودیت‌ها

- **Producer فقط ۳۰۰٬۰۰۰ ردیف اول فایل** را می‌خواند (حدود چهار روز اول ژانویه) و با `random_state=42` همیشه همان ۹۰۰۰ سفر را می‌فرستد. آمار استریم نمونه‌ای از این بازه است و با آمار کل ماه دقیقاً یکی نیست. نمونه‌ای از شواهد: میانگین مسافت پنجره‌های استریم بین ۳٫۵ و ۴٫۰ مایل بود، در حالی که میانگین کل ماه ۳٫۳ مایل است؛ میانگین چهار روز اول (از جدول روزانه) حدود ۳٫۹ مایل می‌شود، که با استریم سازگار است. سهم JFK در استریم هم بیشتر از کل داده است.
- جدول‌های استریم تجمعی‌اند و اجراهای پیاپی Producer جمع می‌شوند.
- زمان‌های اجرای Hadoop هر کدام یک اندازه‌گیری تکی روی Docker هستند و نوسان دارند.
- Hadoop با یک DataNode و `replication=1` اجرا شد؛ مقاومت در برابر خرابی ندارد (در محیط واقعی معمولاً ۳).
- Spark در حالت Local و از دیسک محلی می‌خواند، نه از HDFS.
- نمودارها برچسب انگلیسی دارند تا به فونت فارسی نیاز نباشد.

## ۱۶. نتیجه‌گیری و درس‌های آموخته

- **کیفیت داده مقدم بر تحلیل است:** بدون پاک‌سازی، مسافت‌هایی تا ۳۱۲ هزار مایل میانگین‌ها را کاملاً منحرف می‌کردند.
- **Combiner مهم‌ترین بهینه‌سازی MapReduce است:** حجم Shuffle از ۲٫۷ میلیون رکورد به ۷۲ رسید.
- **Streaming سرعت توسعه می‌دهد و Java سرعت اجرا:** برای یک کار یکسان، Java حدود ۱٫۷ برابر سریع‌تر بود.
- **تست محلی با pipe** (`cat | mapper | sort | reducer`) قبل از اجرا روی کلاستر خطاها را در چند ثانیه نشان می‌دهد.
- **اعتبارسنجی بین ابزارها** (شمارش ردیف، `diff` خروجی‌ها، پیام Kafka) به نتیجه اعتماد می‌دهد.
- **ابزار به نیاز:** MapReduce برای فهم مفاهیم، Spark برای کار روزمره و Kafka برای داده زنده.

**کارهای آینده:** خواندن Spark از HDFS، نمونه‌گیری Producer از کل ماه، ذخیره نتایج استریم در پایگاه‌داده یا Parquet، پایش با Grafana و پیش‌بینی تقاضا با Spark MLlib.
